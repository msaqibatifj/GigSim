GigBid: an agent that bids on freelance jobs, with a human in the loop

AI-4016 R&D report · engineering design review · every number cites a file in evals/results/ (or a commit/doc). Repo: https://github.com/msaqibatifj/GigSim · Live: https://gigbid-yabd.onrender.com

Read first. The evaluation is small (14 compact dev jobs, one run each; 30 for retrieval) and the decision thresholds were tuned on those same 14 jobs. On the two low-fit dev jobs the compact set left out, the system bids wrongly on both (§8). GigSim, the personas and the policy pack were not provided, so they are local mocks, and every GigSim outcome (reply, hire) comes from a client model I wrote: reply rates measure agreement with that model, not real clients. The LLM judge failed calibration against my labels (kappa 0.001, §4), so no judge scores are reported.

1. Problem and constraints

A freelancer's bidding loop: find jobs, read them, spot scams, check whether their own work supports the requirements, price a bid under a Connects (bidding-credit) budget, write a proposal, and answer the client. The costly mistakes are: claiming experience they do not have, bidding on scams or free-work requests, leaking contact details, and anything being sent without their say-so.

Never automated: sending a proposal or message, spending Connects, and submitting on the marketplace in live mode (the user confirms the draft on Upwork). Enforced by a LangGraph interrupt() before every write, idempotency keys on every write, and a live adapter whose submit_proposal returns "confirm on Upwork".

Budgets declared (agent/config.yaml): p95 latency 60 s per job, USD 0.02 per job and 0.10 per proposal. Measured on the compact set [decision_eval_open.json]: p95 27.6 s, USD 0.0004 per job and 0.0008 per proposal, 2,172 tokens per job. Open-weight models only: gpt-oss-20b for small nodes, gpt-oss-120b for Writer and Critic, on Groq. Embeddings bge-small-en-v1.5, reranker ms-marco-MiniLM-L-6-v2 (dev-size, CPU-only machine).

2. Architecture

Bid graph (one thread per job): scout, then analyst | risk | matcher in parallel via Send (state reducer for the parallel writes), decide (skip / watch / bid), pricing, writer, claim verifier (unsupported claims removed before the critic), critic (back to writer at most twice), compliance (deterministic policy pack, can block with a reason), approval (interrupt()), idempotent execute. Conversation graph: read, classify (question / negotiation / interview / scam signal), draft (slots from the Workspace server), approval, send. Budgets of 40 steps and 60,000 tokens per thread move a run to a visible needs_attention state. Both graphs are rendered from code in docs/images/.

Marketplace port: one interface (agent/marketplace_port.py), two adapters (GigSim, live Upwork) behind the Marketplace MCP server, chosen by MARKETPLACE_ADAPTER. MCP surface: Portfolio (read), Marketplace (read and write, bearer auth, per-user rate limit, append-only audit log), Workspace (calendar and email drafts, local mock), plus the official Upwork server and a GitHub server (configured, not run; needs a token). 17 tools with schemas, output schemas and annotations, snapshot-tested (docs/TOOLS.md).

Stores: state (checkpointed in Postgres in the deployment, SQLite locally; all my tests used SQLite), execution trace (events table, audit log, LangSmith), and long-term memory (style and outcome, written only through promotion rules: a style pattern needs 2 separate edits, outcome stats need 3 outcomes in a category). Raw tool output and draft text are never stored in memory.

Why each agent exists: Scout (cheap, scheduled, dedupes); Job Analyst (no tools, so injected text cannot reach a tool); Risk Assessor (client history plus a deterministic injection detector OR-ed with the LLM flag); Fit Matcher (the only source of claims); Pricing (market statistics from 1.3M real contracts, the user's floor, Connects); Writer and Critic (strongest model); Compliance Guard (regex and policy, so it cannot be talked out of a rule); Client Liaison.

Setup: 40 tasks with known correct calls, one model call each (gpt-oss-20b, temperature 0); three designs of the same capabilities. I did not write the hypothesis to a file before running, so it is not pre-registered. My prior was that fewer, coarser tools would win on tokens and lose on accuracy.

Claim verification (B3)

Each draft is split into claims, labelled supported / partial / unsupported against the retrieved evidence, and unsupported claims are removed before the Critic. Unsupported claims per proposal: 0.33 before, 0 after (6 proposals) [decision_eval_open.json]. The verifier is an LLM (gpt-oss-20b) judging the same evidence the Writer saw, so it shares its blind spots; I have not measured its precision against human labels.

Where better retrieval did not improve reply rate, and judge calibration

I cannot answer H4 with this simulator. GigSim's outcome() scores a proposal on word overlap with the job, a specific opening, length, price versus budget and client quality; it never looks at which portfolio item was retrieved, so by construction better retrieval cannot move it except through wording. The pipeline-level reply rate was measured only for V3 (0.33, 6 proposals). Judge calibration is done and the judge fails it: on 30 anonymised items scored blind by me (1-5), weighted Cohen's kappa is 0.001, exact agreement 0.10, mean human 3.07 vs mean judge 4.97 (judge_calibration.json). The judge rates nearly everything 5, so no LLM-judge scores are reported as quality evidence, and the "Rubric score" column stays empty; the blind pairwise human panel of §B4 was not run.

7. Signature extension: X2 proposal experiments

Two strategies on the same 30 bid-worthy jobs, same Writer model, evidence and verification, differing only in style rules: A intro-first, B deliverable-first (opens with the exact deliverable, one measurable result, one scoped question). Paired sign-flip permutation test on per-job GigSim reply probability.

Result [ab_experiment.json]: mean reply probability A 0.514, B 0.579, difference +0.065, permutation p = 0.0033; but sampled simulated replies were 17 (A) vs 16 (B), so the effect on the probability does not show up in 30 draws. B's letters were longer (92.5 vs 77.8 words), and GigSim rewards a specific opening and a 60-220 word length, so a good part of "B wins" is the simulator's own assumptions. It demonstrates the experiment pipeline, not an effect on real clients.

9. Safety and platform respect

GigBid must never: send or spend without approval; claim unsupported experience; follow instructions inside job posts or client messages; leak contact details or payment data into logs; scrape, automate a browser, or poll like a scraper; auto-reply to a scam signal. Enforced by: interrupt() plus idempotency keys; claim verification; posts delimited as untrusted, closing tags neutralised, injected sentences scrubbed before drafting, a regex detector OR-ed with the LLM flag; PII masking at log-record creation and in traces; OAuth tokens Fernet-encrypted and never returned or logged; every query scoped by user; live mode scouts at most every 6 hours and creates drafts only.

Attack success on 6 planted posts: 0.667 before the code-level defences, 0.0 after [injection_eval.json]; the planted word reached a draft in 50% before, 0% after. What still gets through: the detector is regex-based, so a paraphrased or non-English instruction passes it and only the LLM flag and the human approval gate remain (the LLM flag varies between runs); a post that sounds like a hiring manager asking a "screening bot" to say a word is the example that would beat the regex. n = 6, so the 0.0 is not a guarantee.
